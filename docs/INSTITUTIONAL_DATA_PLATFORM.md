# EventRisk Institutional Data Platform v1

## Product boundary

EventRisk provides event-data primitives and normalized intelligence. It does not prescribe portfolio weights, trades, scenario P&L, or investment decisions.

### Layer 1 — Observed
- Source contracts and their version history
- Raw source payload snapshots from the institutional migration forward
- Bid/ask, midpoint, last trade, displayed probability
- Volume, open interest, liquidity, spread and depth when the source provides them
- Source, observed, received and processed timestamps
- Resolution rules, status and deadlines

### Layer 2 — Normalized
- Stable EventRisk canonical event IDs
- Event families and ontology fields
- Cross-source mappings with mapping type, confidence, method and review state
- Entity and instrument masters
- Factual, source-asserted and inferred graph edges as distinct trust classes
- Evidence and provenance for graph edges
- Revision and quality-issue history

### Layer 3 — Optional derived analytics
Existing retail relevance scores, event/security coefficients and portfolio calculations remain separate from the institutional data contract. Institutional clients can ignore this layer entirely.

## Non-negotiable data rules

1. Source contracts are never silently collapsed into canonical events.
2. Raw observations are append-only; corrections create new records.
3. `source_observed_at`, `received_at` and `processed_at` are separate concepts.
4. Inferred relationships are always labeled `edge_class=inferred` and include method/version metadata.
5. A `mentions` or `concerns` relationship is not the same as `affects`.
6. Cross-source disagreement is preserved; source probabilities are never discarded in favor of a single composite.
7. Historical revisions are recorded rather than silently rewritten.
8. Legacy data is not upgraded beyond what was actually stored. The pre-institutional collector did not preserve full raw payloads, so those observations are explicitly labeled legacy.
9. Stable internal IDs are the system of record; LEI/FIGI and other external identifiers are interoperability mappings, not primary keys.
10. Source licensing/redistribution entitlement is tracked separately from technical availability.

## Mapping types

Initial controlled vocabulary:

- `same_event` — semantically equivalent outcome and resolution conditions
- `same_family` — related horizon/theme but not equivalent event
- `narrower_than`
- `broader_than`
- `overlaps_with`
- `conditional_on`
- `complement_of`
- `mutually_exclusive_with`
- `legacy_existing_mapping` — imported from the pre-institutional system and not yet reviewed under the institutional mapping policy

Mapping review status should use a controlled vocabulary such as:

- `unreviewed`
- `auto_high_confidence`
- `human_reviewed`
- `ambiguous`
- `rejected`
- `legacy_unreviewed`

An embedding/LLM similarity score may propose candidates but must never by itself convert two contracts into the same canonical event.

## Graph trust classes

- `factual` — externally verifiable relationship with evidence/provenance
- `source_asserted` — faithfully represents a named source assertion
- `inferred` — generated by rules/models/LLMs; must include inference method and method version

Clients must be able to exclude inferred edges.

## Point-in-time behavior

Institutional research requires two different historical questions:

1. What do we currently believe was true at time T?
2. What did EventRisk know at time T?

The v1 schema therefore preserves source observation, receipt, processing and validity timestamps. Future API work should add explicit `as_of` modes rather than silently serving revised history.

## API v1 initial surface

Read-only endpoints in `institutional_api.py`:

- `GET /v1/events`
- `GET /v1/events/{event_id}`
- `GET /v1/events/{event_id}/history`
- `GET /v1/events/{event_id}/relationships`
- `GET /v1/entities/{entity_id}`
- `GET /v1/entities/{entity_id}/relationships`
- `GET /v1/changes`

Next planned surfaces:

- source contract/version endpoints
- explicit point-in-time/as-of queries
- term-structure endpoint
- mapping-review metadata endpoints
- bulk Parquet exports
- streaming/WebSocket change feed
- authenticated client/service accounts

## Production gates before institutional use

- Confirm commercial ingestion/storage/redistribution rights per source
- Full raw-payload capture enabled for every live adapter
- Mapping QA and review queue operational
- Point-in-time reconstruction tests passing
- Automated source freshness and anomaly checks
- Staging and production separated
- API authentication, scopes and key rotation
- Audit logging
- Backups and restore test
- Published data dictionary and revision policy
- Load/latency testing and observable service-level metrics
- Security review and vulnerability management
- Legal/compliance review of data licenses and customer terms

## Migration files

- `institutional_schema.sql` — additive institutional schema
- `migrate_institutional.py` — schema installer
- `institutional_backfill.py` — transparent migration of legacy numerical observations and mappings
- `institutional_api.py` — first read-only institutional API

Do not run the migration against production until it has been exercised against an isolated staging database and the backfill row counts/constraints have been verified.
